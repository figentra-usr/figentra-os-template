# Architecture

This section holds the architecture plan: the single document (or small set of documents) that describes how the application is put together — service boundaries, data ownership, the tenancy model, and the decisions that don't fit cleanly into a single ADR because they're the backdrop every ADR is written against. When it exists, it is the current authority: where a runbook, a standard, or a product blueprint seems to disagree with it, the plan wins.

It's written and kept current by whoever owns the overall system design — typically a lead engineer or an architecture-guardian role — and it changes rarely, deliberately, and usually alongside an ADR that records why.

**Nothing has been written here yet.** This is a blank template; no architecture plan exists until this product's first one is drafted. Start one as soon as there's a real shape to describe — a single service, a couple of tables, a first tenant model — rather than waiting for the full picture.
